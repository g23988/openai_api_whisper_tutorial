Chapter 7

Prompt 基礎

上一章我們打通了第一通 API call。短短十行，模型有回應。但你大概很快就會發現一件事：同樣一個問題，問十次有十種答案——有時候是條列、有時候是長篇大論、有時候很官腔、有時候很生硬。

這不是模型壞了，是因為你還沒學會跟模型講話。

這章我們把「Prompt」這件事好好講清楚。學完之後，你會發現「同一個模型」在你手上跟在別人手上產出的品質可以差很大——差別不在模型，在你怎麼問。

Prompt 是什麼

Prompt 就是你給模型的指示。最直觀的理解是：

response = client.responses.create(
    model="gpt-4o",
    input="幫我改寫這段話",
)

這個 input 就是 prompt。

但實際上 OpenAI Responses API 允許你分開「告訴模型它是誰」（instructions）跟「這次的具體輸入」（input）：

response = client.responses.create(
    model="gpt-4o",
    instructions="你是一位專業的中文編輯，請保留原意並讓文字更清楚。",
    input="今天那個東西可能有點問題我們晚點再看。",
)

兩個放在一起就是這次呼叫的完整 prompt。這個區分很重要——instructions 設定「角色與規則」，input 給「這次的具體素材」。如果你做一個改寫工具會反覆呼叫 100 次，instructions 是固定的，input 每次不同。

Tip "Prompt engineering" 這個詞是 2020 年 GPT-3 發布之後才大規模出現的。在那之前模型不夠強，輸入只是「給它一段文字看它能不能接得下去」；GPT-3 突然好到「你告訴它要做什麼，它就做」，但同時「怎麼告訴它」變成關鍵技能。一兩年內這變成一個獨立的職位類別。今天「prompt engineer」這個職位有點退燒——因為新一代模型對細節越來越不敏感、容錯越來越高——但「會講話」依然是用 API 最重要的單一技能。

從爛 prompt 到好 prompt

我們用一個例子貫穿這節：你想做一個「把口語轉成正式 email」的工具。

第一版 prompt（很爛）：

input="幫我寫個 email"

模型不知道要寫什麼、給誰、什麼風格。它會猜——而它的猜往往不是你想要的。

第二版（好一點）：

input="幫我把這段話改成 email：明天客戶會議延後到下午三點"

模型現在知道任務了：改寫成 email。但它仍要猜：給誰寄？正式還是輕鬆？要不要署名？

第三版（清楚很多）：

instructions="""
你是一位協助使用者撰寫商務 email 的助手。
規則：
1. 使用繁體中文
2. 語氣專業但不僵硬
3. 開頭加上適當問候，結尾用「祝 順心」
4. 不要加任何不在原文裡的資訊
""".strip()

input="把這段口語改成 email，收件人是「林經理」，內容：明天客戶會議延後到下午三點"

現在模型有完整資訊：角色、語言、語氣、格式規則、不能編造、收件人、內容主旨。輸出會穩定多了。

好 prompt 的四個元素

把上面這個例子拆開，一個好 prompt 通常包含四個元素：

1. 任務（Task）：你要它做什麼？「改寫」「翻譯」「摘要」「分類」要明確。

2. 背景（Context）：補充資訊。誰會看、用在哪、有什麼限制。

3. 限制（Constraints）：明確的「不要做什麼」。例如「不要編造資訊」「字數不超過 200 字」「不要用 emoji」。

4. 格式（Format）：輸出長什麼樣。條列、段落、JSON、表格、Markdown。

不一定每次都四個都要寫——簡單任務一句話就夠。但任務必明確，這是最低標。

Note 你可能會發現一個有趣的事：寫 prompt 跟「給新同事下指示」非常像。差勁的 prompt（「幫我搞一下」）就像差勁的主管下單——對方只能猜你的意思。好的 prompt 把任務、限制、格式都講清楚，就像會帶人的主管。這個技能很值得你刻意練習，因為好的 prompt 工程跟好的人類溝通是同一套能力。

角色設定的細節

instructions 裡常會設定一個「角色」：

instructions="你是一位專業的中文編輯..."
instructions="你是一位資深的程式碼審查員..."
instructions="你是一位用簡單語言解釋複雜概念的老師..."

這招很有效，但也容易被誤用。幾個原則：

好的角色設定會限縮模型的行為範圍：

instructions="""
你是一位專業的中文編輯，專長是讓口語化文字變得清晰有條理。
你只負責改寫，不評論、不解釋、不提建議。
直接輸出改寫後的文字，不要說「以下是改寫」這類前綴。
""".strip()

沒用的角色設定只是裝飾：

instructions="你是一位非常聰明的 AI 助手，會盡力幫助使用者。"

這種寫法等於沒寫——模型本來就會盡力幫你。角色設定的價值是「定義你不要什麼」，而不是「定義你要什麼」。

指定輸出格式

如果你寫的是「會被另一個程式讀」的工具，輸出格式比內容更重要。最常見的兩個技巧：

1. 用範例（few-shot）：

instructions="""
判斷使用者輸入的情緒，輸出格式：

情緒：[正面 / 負面 / 中性]
信心：[0-100]
關鍵字：[最多三個]

範例：
輸入：今天的會議真的太棒了，大家都很投入
情緒：正面
信心：90
關鍵字：會議、投入、滿意
""".strip()

input="這個產品爛透了，根本不能用"

這比文字描述「請輸出包含三個欄位的文字」有效十倍。

2. 用結構化輸出：

如果你真的需要乾淨的 JSON，不要靠 prompt 寫「請輸出 JSON」——那是不可靠的。本課 Chapter 13 會教 OpenAI 的 response_format 機制，可以強制模型輸出符合特定 schema 的 JSON。

Warning 一個很常見的錯誤：在 prompt 裡寫「請輸出 JSON 格式：{"sentiment": "...", "score": ...}」，然後試圖用 json.loads() 解析回傳。這在 95% 的情況會成功，但剩下 5% 會炸——模型偶爾會在 JSON 前後加「以下是分析結果」之類的話。要嘛接受這個失敗率、寫 try/except，要嘛用 Chapter 13 教的結構化輸出。

Temperature：模型的「亂度」

temperature 是個 0 到 2 的數字，控制模型回答的「隨機性」：

response = client.responses.create(
    model="gpt-4o",
    input="寫一個短句",
    temperature=0.0,   # 幾乎一致的輸出
)
  • temperature=0：每次幾乎都回一樣的答案，適合「事實查詢」「程式碼生成」這種需要可預測性的任務
  • temperature=1.0（預設）：有變化，適合一般用途
  • temperature=1.5 以上：很有創意但開始胡言亂語

本課的工具大多用 0 到 0.7 之間。temperature=0 看似最「準」，但有時候模型會卡在一個錯誤答案重複輸出，不總是最佳選擇。

Tip Temperature 這個詞來自統計物理。你不需要懂背後的數學——只要知道數字小 = 穩定、數字大 = 多樣就夠了。實務上 0.3 到 0.7 是最常用的範圍。

一個完整範例：中文改寫工具

把這章學的東西整合起來，做一個可重複呼叫的中文改寫工具：

from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()
client = OpenAI()

INSTRUCTIONS = """
你是一位專業的中文編輯，專長是讓口語化的文字變得清晰、有條理、好閱讀。

規則：
1. 使用繁體中文
2. 保留原意，不要加上沒講過的資訊
3. 不要改變語意或結論
4. 不要評論，直接輸出改寫後的文字
5. 不加前綴（例如「以下是改寫」）
""".strip()

def rewrite(text: str, temperature: float = 0.3) -> str:
    response = client.responses.create(
        model="gpt-4o",
        instructions=INSTRUCTIONS,
        input=text,
        temperature=temperature,
    )
    return response.output_text

if __name__ == "__main__":
    sample = "今天那個會議啊大家講的好像有點亂客戶那邊也沒太理解"
    print(rewrite(sample))

跑一次，輸出大概像：

今天的會議內容有些雜亂，客戶似乎也沒有完全理解。

這個工具現在可以重複呼叫——rewrite() 可以丟進任何一段文字，每次都會用同樣的規則改寫。本課從這裡開始，我們會反覆使用「instructions + input + 函式包裝」的模式。

小結

  1. Prompt = instructions（角色與規則）+ input（具體素材）——清楚分開兩者
  2. 好 prompt 的四元素：任務、背景、限制、格式
  3. 角色設定的價值是「定義不要什麼」，不是裝飾
  4. 指定輸出格式：先用範例，需要程式可讀的 JSON 用 Chapter 13 的結構化輸出
  5. temperature：0 穩定、1 預設、太高會胡言亂語
  6. 把 prompt 包進函式：方便重複使用，固定 instructions 變動 input

下一章我們把這個改寫工具擴充成完整的「文字小工具」——接命令列參數、處理檔案、加上各種選項。

練習

  1. 改 INSTRUCTIONS，讓模型把口語轉成正式商務 email（含問候與結尾）。
  2. 加一個 style 參數，可以是 "短"、"中"、"長"，分別在 instructions 裡加上對應的字數限制。
  3. 試試把 temperature 從 0 改到 1.5，同一段輸入跑五次，比較穩定度的差異。
  4. 寫一個 prompt，要求模型輸出「情緒：[正面/負面/中性] | 信心：[0-100]」格式，並用 Python 解析回來。寫 try/except 處理偶爾的格式錯誤。
